# 소설 → AI 애니메이션 (「이야기 만들기」) — 설계 (2026-10-10, 프론트 담당 초안)

> 상태: **M0·M1·M2·M3 구현 완료, M4 진행 중.** 구현 상태의 기준은 `docs/00_NOW.md`이며, M4 세 항목 구현과 통합 검증 뒤 실사용 확인을 한다.
> ⚠ 「분석 없이 바로 만들기」(M0)는 원문을 프로젝트 개요에 저장한다(§2-1). AI 분석을 거치는 M1→M2 경로는 원문 대신 구조와 출처 메타데이터를 프로젝트에 전달한다.
> 근거: 캡틴D 요청(2026-10-09~10) · Codex 조사 1305(Reddit 조건) · 기존 장기 프로젝트 계약(`packages/shared/src/api.ts`).

## 1. 목표와 비목표

**목표:** 캡틴D가 소설·이야기를 넣으면, 앱이 읽고 **줄거리·인물·회차 구성**을 정리해 보여 주고, 캡틴D가 확인·수정한 것으로 **장기 프로젝트(회차별 릴스)** 를 만든다. 사람이 하는 일은 *넣기 → 확인하기 → 승인하기*이고, 설정 칸을 직접 채우지 않는다.

**비목표(이번 설계에서 뺀 것):**
- 시리즈 게시(다음 화 예고를 영상에 넣기) — 회차별 게시는 기존 게시 화면 그대로.
- Reddit 주소로 글 자동 가져오기 — Reddit의 사전 승인·이용 조건 때문에 만들지 않는다(Codex 1305). 글은 직접 붙여넣는다.
- 원문을 그대로 영상화 — 목표는 **재창작**이고, 그것을 구조로 강제하는 것은 M1~M2의 「추상 구조」(§3)다. M0는 지시문뿐이다.

## 2. 핵심 구조: 장기 프로젝트의 **앞문**

새 파이프라인을 만들지 않는다. 회차 개요 → 대본 → 그림 → 영상 → 병합 → 게시는 장기 프로젝트가 이미 한다. 이야기 만들기는 그 앞에 서서 **지금 사람이 손으로 채우던 것(설정·회차 개요·주인공)을 소설에서 뽑아 채워 주는** 단계다.

```
소설 붙여넣기 ─▶ ① AI 분석(1회, 승인 게이트) ─▶ ② 확인·수정 화면 ─▶ ③ 장기 프로젝트 생성(설정+회차 개요 채움)
                                                      │
                                                      └▶ ④ 인물 확정(보관함 짝짓기 / 새 이미지) ─▶ 기존 회차 흐름
```

| 사람이 지금 하는 일(장기 프로젝트) | 이야기 만들기가 대신 채우는 것 | 재사용하는 기존 계약 |
|---|---|---|
| 제목·한 줄 줄거리·개요·장르·분위기 입력 | 분석 결과의 같은 필드 | `CreateLongProjectRequest.settings` |
| 「회차 개요 미리보기」→(유료)승인→AI가 회차 개요 생성, `outline_status`가 `outline_ready`로 바뀌고 회차 작업 파일이 만들어짐 | 분석이 이미 만든 회차 구성을 넣고 싶지만, **기존 `PATCH …/episodes/:n/outline`은 그 칸의 글만 바꿀 뿐 상태 전이·회차 파일 생성을 하지 않는다** → POST→PATCH 몇 번으로 개요 AI 호출을 대체해 회차 대본으로 진행할 수 없다. M2에 **확정된 구조를 받아 상태·회차 파일을 안전하게 초기화하는 백엔드 단일 경로**가 필요 | 신규 백엔드 경로(M2) |
| 주인공 캐릭터 폴더 연결 | 분석의 주인공 인물 ↔ 보관함 캐릭터 | `story-bible/protagonist-asset-link` |
| 조연 | **연결할 곳이 없음**(장기 프로젝트에 조연 계약 없음) | 신규 필요(M4) |

### 2-1. 현재(M0)의 실제 동작과 한계 — CLI 1310

- 「이야기 만들기」는 붙여넣은 소설 **원문 전체를 `settings.overview`로** `POST /long-projects`에 보낸다. 서버는 그것을 **저장**하고, 회차 나누기(개요 AI)의 프롬프트 「세계관·전체 줄거리」에 **넣는다.** 즉 M0에서는 원문이 저장되고 기존 개요 AI가 원문을 읽는다.
- 재창작 지시는 프로젝트 `notes`에 글로 들어가지만 **원문 복사를 구조적으로 막지는 않는다.** 그래서 화면은 「다시 씁니다」를 약속하지 않는다.
- 회차 수·장면 수는 기본값(3·6)으로 생성되고, 조절은 장기 프로젝트 **설정**에서 한다(회차 나누기 화면은 `preview.episodeCount`를 보여 줄 뿐 조절 UI가 없다).
- 원문 저장 정책(저장할지·해시만 둘지)과 분석 설계는 Codex가 별도 검토한다.

### 2-2. M1 확정 설계 — Codex

- **입력 한도:** M1은 화면과 서버 모두 6,000 JavaScript 문자열 글자까지 받는다(화면 M0 한도와 같음). M4 긴 글 확장에서는 최대 120,000자를 받으며, 60,000자 이하는 기존 1회 분석, 초과 입력은 60,000자 이하 조각별 추상 요약 후 합성한다. 제목 120자·한 줄 설명 500자·출처 메모 500자, 회차 1–20, 회차당 장면 2–12.
- **Provider:** 무료 할당량에 기대지 않고 앱의 기존 OpenAI 연결·월 예산을 쓴다. 현행 대본과 같은 `gpt-5.6-luna`; Responses API의 structured output으로 계약된 구조를 검증한다. 정확한 프롬프트·비용·입력 길이를 미리 보여 주고 명시적 승인 뒤 호출한다. 예상 비용은 `$0.05/회`로 보수 추정하고 OpenAI 장부에 기록한다. 기준 모델의 공식 공개 단가는 입력 `$0.20`/출력 `$1.20` per 1M tokens이며 변경될 수 있다(2026-10-10 확인, [모델 안내](https://developers.openai.com/api/docs/models/gpt-5.6-luna)).
- **원문 저장:** 애플리케이션 디스크에는 원문을 저장하지 않는다. 동일 입력 재사용에는 원문·설정·출처 메모를 합친 SHA-256을 쓰고, 권리 확인 시각·제목·선택 출처 메모·모델·회차/장면 수·추상 분석만 `learning_data/story_sources/`에 둔다. API 요청에는 `store:false`를 지정한다. OpenAI 측 보존은 이 앱의 로컬 저장 설정과 별개다.
- **이름 재창작:** 모델에 사람·장소의 고유 이름과 대사·독특한 사건 배열을 새로 만들라고 명시한다. M1은 구조화 결과의 형식·회차 수를 검증하지만 텍스트 유사도를 법적 판정처럼 보증하지 않는다. M2부터 프로젝트 프롬프트에는 저장한 구조만 전달하고 원문 필드는 제공하지 않는다.
- **중복·실패:** 입력 해시 기준으로 성공 결과를 재사용한다. 승인 직전 독점 claim을 디스크에 기록하고, 모호한 Provider 실패의 claim은 유지해 동일 입력의 재전송을 막는다(D-005). 다른 문구로 바꿔 새 분석을 하는 경우는 새 입력으로 보고 다시 미리보기·승인한다.

## 3. 단계별 설계

### ① AI 분석 — 미리 보고, 승인하고 나가는 호출
- **입력:** 소설 본문(M1 6,000자; M4 확장 상한 120,000자, 60,000자 이하 부분 단위) + 권리 확인(필수) + 출처 메모(선택).
- **호출 방식은 프로젝트의 기존 원칙대로:** 프롬프트·예상 비용을 **먼저 보여 주고**, 사람이 승인해야 나가며, 입력 해시를 저장해 같은 요청을 두 번 보내지 않는다(「돈이 나가는 호출」 D-005·D-010 계열). 화면을 열거나 미리보기만으로는 유료 요청이 나가지 않는다.
- **출력 = 「추상 구조」(`StoryAnalysis`):** 원문 문장을 담지 않는다.
  - 한 줄 줄거리 · 장르 · 분위기 · 주제
  - 인물(`id, name, role(주인공/조연), appearance, personality`) — **이름은 새로 지은 것**(실명·고유명사 대체 제안)
  - 회차 구성(`episode, title, summary, mainEvent, conflict, cliffhanger, nextEpisodeHook`)
  - 주의 표지(`warnings`): 민감한 내용(폭력·성적 내용·미성년자·자해), 실존 인물·개인정보 의심 — 이미지·영상 제공자 거절을 미리 알린다.
- **왜 추상 구조인가(M1~M2의 목표, M0는 아님):** Codex 1305의 재창작 검증 원칙(원문 대사·고유 이름 제거 후 새 인물·배경·사건)을 **구조로 강제**한다. 이후 모든 프롬프트(회차 대본·그림)는 원문이 아니라 이 구조만 읽는다. 원문은 분석 요청에만 쓰이고 프로젝트 프롬프트에는 들어가지 않는다.
- **저장:** `story_source`(원문 해시·권리 확인 사실·출처 메모·분석 결과·프롬프트 해시)를 프로젝트 옆에 둔다. 원문 전문을 저장할지는 Codex 판단(저장 안 하고 해시만 두는 안 권장).

### ② 확인·수정 화면 — 이 기능의 핵심 화면
- 「AI가 이렇게 읽었습니다」: 줄거리·분위기 / **인물 카드**(이름·외모·성격·역할, 고치기·합치기·빼기) / **회차 목록**(제목·핵심 사건·마지막 궁금증, 고치기·순서·회차 수 조절) / 주의 표지.
- 사람이 고친 것이 최종이다(분석은 제안일 뿐 — 밈 관찰 카드의 「제안과 카드는 다른 층」 원칙과 같다).
- 이 화면까지는 **돈이 더 나가지 않는다.**

### ③ 장기 프로젝트 생성 (M2 — 백엔드 단일 경로)
- 확정한 구조(설정 + 회차 개요 + 주인공)를 **한 번에 받아** 장기 프로젝트를 만들고, 회차 개요 칸을 채우고, `outline_status`와 회차 작업 파일을 **안전하게 초기화**하는 백엔드 경로가 필요하다. 기존 개요 승인 경로가 맡는 상태 전이·파일 생성을 이 경로가 대신 맡아야 하며, 중간에 실패해 반쯤 만들어진 프로젝트가 남지 않아야 한다(원자성). 프론트가 `POST`→`PATCH`를 여러 번 부르는 방식은 **쓰지 않는다**(상태가 안 바뀌어 회차 대본으로 진행 불가).
- 구현: `POST /long-projects/from-story-analysis`가 검토된 `settings`·`analysis`·원문 없는 `source` 메타데이터를 한 번에 받는다. `project.json`을 `outline_ready`로, 회차 개요 전체를 같은 상태로 기록하고 인물 카드·주의 표지·선택한 주인공 Asset 폴더 링크를 Story Bible에 둔다. 원문은 받지 않으며 M1 출처 메타데이터만 `novel_story_source.json`에 보존한다. 최종 회차 수는 사람이 편집할 수 있고, `source`의 회차·장면 수는 최초 분석 요청 그대로 둔다. 기존 `<projectId>` 폴더 안에서 `long_story` 임시 폴더를 완성한 뒤 rename하므로 짧은 프로젝트와 ID를 공유할 수 있고, 실패한 긴 프로젝트의 절반 상태는 공개하지 않는다. 이미 `long_story`가 있으면 해당 폴더를 보존하고 실패한다.
- 만든 뒤 사용자는 장기 프로젝트의 회차 화면으로 간다(대본 승인 이후는 기존 흐름과 승인 게이트 그대로). 자동 개요 AI 호출은 건너뛰며 이후 대본 생성의 기존 승인 게이트는 그대로다.

### ④ 인물 확정과 캐릭터 이미지
- **짝짓기(지금 가능):** 인물 카드마다 보관함 캐릭터를 고른다(폴더·낱장). 주인공은 `protagonist-asset-link`로 연결.
- **새 이미지 만들기(M3 완료):** 검토된 인물의 이름·외모·성격만 프롬프트에 넣어 이미지 한 장을 만들고 캐릭터 폴더와 정면 그림으로 등록한다. 미리보기·별도 승인·입력 해시 중복 방지·월 예산을 거치며, 모호한 실패 뒤 재전송하지 않는다. 사람이 결과를 보고 선택하면 장기 프로젝트에 연결한다. 계약은 `docs/04_INTERNAL_API_CONTRACT.md` M3 절.
- **조연(M4):** 검토한 조연 카드마다 기존 보관함 캐릭터 폴더를 명시적으로 연결한다. 프로젝트 생성 때 선택하거나 설정에서 바꿀 수 있다. 연결은 이미지가 아직 없는 회차에만 자동 매핑되고, 수동 매핑·제외·이미지가 있는 회차는 보존한다. 이 연결 수정은 Provider를 부르지 않는다.

### ⑤ 회차 보드(M4)
- 회차를 행으로, 대본·그림·영상·병합을 단계 칸으로 보여 주고 각 칸에서 이어갈 화면으로 이동한다. 기존 장기 프로젝트 상세의 목록·검색·상태 필터·타임라인 편집과 단계별 누계는 유지한다.

## 4. 안전·권리 원칙(이 기능 전체)

1. 유료 호출은 항상 미리보기→사람 승인→해시 중복 방지. 자동 재시도 없음.
2. 권리 확인 체크 없이는 분석을 보내지 않는다. 확인 사실은 프로젝트에 남는다.
3. (M1~M2 이후) 원문 문장·대사·고유 이름이 영상·게시물로 나가지 않게 **추상 구조 경유**를 강제한다. M0에서는 지시문뿐이다. 유사도 기계 점검은 보조 표지일 뿐 권리 해결을 주장하지 않는다(Codex 1305).
4. Reddit 자동 수집·비공식 `.json`/스크래핑 금지.
5. 분석 결과·확인 화면은 열기만으로 유료 호출이나 프로젝트 생성을 하지 않는다. 사람이 구조를 수정한 뒤 확정 버튼을 눌러야 프로젝트를 만든다.

## 5. 구현 단계 (작게, 각 단계가 혼자서 쓸모 있게)

| 단계 | 내용 | 담당 | 끝났다는 뜻 |
|---|---|---|---|
| **M0** (지금) | 입력 화면을 **소설 + 권리 확인 + 제목·한 줄 줄거리**로 줄이고(분량 칸은 기본값), 만든 뒤 곧바로 장기 프로젝트의 「회차 개요 미리보기」로 이어지게 한다. AI·계약 변경 없음. | 프론트 | 소설을 붙여 장기 프로젝트가 만들어지고 다음 화면이 개요 단계로 열린다. 테스트·실화면(읽기 전용) |

## 6. 열린 질문 (Codex·캡틴D)

- ✅ M1 결정 — 입력 6,000자, 원문 파일 저장 안 함; `gpt-5.6-luna`+회당 `$0.05` 선견적; 모든 인명·지명 재창작 지시(텍스트 유사도 보증은 안 함). M4는 최대 120,000자를 60,000자 이하 조각으로 처리하고 호출 수에 비례해 비용을 미리 계산한다.
- ✅ 3단계 생성은 **서버 단일 경로로 확정**(상태 전이·원자 저장 때문). 요청은 `POST /long-projects/from-story-analysis`; 검토 결과와 원문 없는 출처 메타데이터를 받고 임시 디렉터리 rename으로 실패 시 반쪽 프로젝트를 노출하지 않는다. 기존 ID 충돌은 보존하고 거절한다.
